# Data flow diagrams (Yourdon / DeMarco)

A data flow diagram (DFD) shows the main data workflows of a system: what comes in, what the system
does with it, where it is kept, and what goes back out. Keep them high level. A few processes, the
stores they use and the datasets that move are enough. Other diagrams (sequence, ER, flowcharts)
explain the detail. If the user requires a lower, more granular DFD, see [lld-notation.md](lld-notation.md).

- [assets/templates/data-flow-diagram.drawio](../assets/templates/data-flow-diagram.drawio):
  a small order-system template, generated by `scripts/dfd_builder.py --example`

## 1. Page

The diagram is a single page, `Data flow diagram`. It shows the main processes inside the system
(3 to 6), the data stores they use, the externals outside the boundary, and the arrows between them.

## 2. Notation

| Element | Looks like | Meaning | Builder call |
|---|---|---|---|
| Process | Grey oval | Work the system does. Name it with a short verb phrase | `page.process("ingest", "Ingest upload", x, y)` |
| Data store | Two parallel lines | Data kept between steps, such as a table or a file | `page.store("orders", "Orders", x, y)` |
| External | Blue rectangle | A user or service outside the system | `page.external("op", "Operator", x, y, kind="user")` |
| Data flow | Arrow | One dataset moving from one place to another | `page.flow("op", "ingest", "Registration CSV file", "CSV upload")` |
| Boundary | Dashed box | The system. Processes and stores go inside, externals stay outside | `page.boundary("System", x, y, w, h)` |
| Duplicate store | Store with `*` | Last resort only: the same store drawn again. Readers see two datasets, so avoid it (see [Layout](#6-layout)) | `page.store("orders", "Orders", x, y, duplicate=True)` |

Name each arrow in plain English (`Staged registrations for review`) and add the technology it
lives in or travels through as a source tag (`Staged registrations for review [Postgres]`,
`Upload file [S3]`, `Session [Redis]`). Give the same tag to a store's label (`Upload workspace (Postgres)`).
Keep the small note under the name to a few words, and only when the name alone is unclear. Longer
explanations go in your reply, see [Keep the diagram light](#keep-the-diagram-light).

One arrow is one dataset from one source. If two datasets come from different places (different
stores, externals or processes), or sit in different technologies, draw two arrows. Never bundle them
into one arrow such as `Records and settings`.

The `dfd=` style keys are for the linter only. draw.io keeps them and ignores them.

## 3. Scope: what goes inside the boundary

- Only the system under study goes inside. Anything else is an external, even if you have its code.
- Shared services owned by someone else (a virus scanner, a licence register) are externals.
- Scheduled jobs are not externals. Show them as a process and put the schedule in the small note (`Daily`).
- A store that is only written here and read elsewhere (a log) gets `io="sink"`. A store that is kept
  elsewhere and only read here (settings) gets `io="source"`.

## 4. Keep it high level

| Detail found in the code | What to do |
|---|---|
| Validation checks and rules | Fold them into the process that runs them. Say "Validate rows", not each rule |
| Several tables used together | Draw one store, such as "Upload workspace" |
| Endpoints, function names, error codes | Leave them out, or add a short note if a reader needs them |
| Field-by-field mappings | Leave them out. This is not a schema |
| Gateways, CDNs, load balancers | Leave them out, or merge them into the process that handles the request |

Name processes with verb phrases and arrows with plain noun phrases. Aim for 3 to 6 processes on the
data flow page. Nothing has to be exhaustive: other diagrams explain the rest.

## Keep the diagram light

Put only shapes, arrow names and source tags on the diagram. Notes, assumptions, known gaps, caveats
and rationale go in your reply as short bullet points after the diagram, not in `note:` cells or long
arrow notes. Add a note to the diagram only when a reader cannot follow the flow without it, and say
why in your reply.

## 5. Rules (enforced by `scripts/dfd_lint.py`)

| Rule | Severity | Meaning |
|---|---|---|
| R1 | ERROR | Every arrow touches a process. No external-to-store or store-to-store arrows |
| R2 | ERROR | Every arrow has a name |
| R3 | ERROR | Every process has at least one arrow in and one arrow out |
| R4 | ERROR | Externals sit outside the boundary. Processes and stores sit inside it |
| R5 | WARN | Every store is both written and read, unless it sets `io` to `sink` or `source` |
| R6 | WARN | No arrow passes through a shape other than its own start and end |

Run it on any DFD, including hand-drawn ones (roles then come from shape heuristics):

```bash
python .agents/skills/draw-io-diagram-generator/scripts/dfd_lint.py docs/my-dfd.drawio --strict
```

## 6. Layout

- Put externals on the outer left and right, outside the boundary. Processes and stores go inside it.
- Put each store between the processes that write and read it.
- Draw each dataset or store once, in a single box, so the real relations (who writes it, who reads it)
  are visible. A second box looks like a second dataset. Place the store between its writers and readers.
- If an arrow would cross the diagram, route it with `via=` waypoints or `exit=`/`entry=` and move
  shapes first. Use `duplicate=True` only when no clean layout exists, and say so in your reply.
- Use `via=` waypoints, or `exit=` and `entry=` to pin where an arrow starts and ends, so arrows stay
  clear of shapes.
- Put the legend outside the boundary. Give titles enough width that they do not run into externals.

## 7. Workflow

1. Read the source (code, schema, configs, sample data). List the externals, processes, stores and arrows.
2. Write a short spec script next to the diagram (see the example in `SKILL.md`). Build the data flow page.
3. Run it. `DfdDocument.write()` writes the file and runs `dfd_lint`. Fix every ERROR. Fix each WARN,
   or say why it stays.
4. Validate the XML: `python .agents/skills/draw-io-diagram-generator/scripts/validate-drawio.py <file>`.
5. Render and look: `python .agents/skills/draw-io-diagram-generator/scripts/render-preview.py <file> --out /tmp/preview/preview.html`,
   serve the folder, open it in the browser tool and check each page. Fix overlapping labels and cramped text.
6. Repeat 3 to 5 until clean, then delete the preview files.
